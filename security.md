# Security Rules — Touchpoint

> **Read this before writing any code or creating any plan.**
> Apply every rule below to any new code. If a planned feature conflicts with a rule, flag
> it before implementing and propose a compliant approach.

---

## Input Validation

- Validate and sanitize ALL user-supplied input at system boundaries (API routes, form handlers, CLI args)
- Never trust request bodies, query params, headers, path segments, or cookies without validation
- Use schema validation for all API payloads (e.g. zod, joi, valibot)
- Reject unknown fields — use strict schema parsing, not loose coercion

## Authentication & Authorization

- Never implement custom auth from scratch — use a proven library (NextAuth, Supabase Auth, Lucia, Clerk, etc.)
- Check authorization server-side on every protected route and action — never trust client-side state alone
- Use short-lived access tokens (JWTs ≤ 15 min); store refresh tokens in `httpOnly`, `Secure`, `SameSite=Strict` cookies
- Never store tokens, passwords, or secrets in `localStorage` or `sessionStorage`
- Always hash passwords with bcrypt, argon2, or scrypt — never MD5/SHA1 alone

## Injection Prevention

- Use parameterized queries or an ORM — never concatenate user input into SQL strings
- Never pass user input to `exec()`, `eval()`, `child_process`, or shell commands
- Sanitize any user-supplied content rendered as HTML (use DOMPurify or framework-native escaping)
- Avoid `dangerouslySetInnerHTML` in React unless the content is already sanitized

## Secrets & Environment Variables

- Never hard-code secrets, API keys, DB URLs, or tokens in source files
- Use `.env` files (gitignored) and validate required variables at application startup
- Never log secrets, tokens, passwords, or PII — scrub them from error messages too
- If a secret is accidentally committed: rotate it immediately, then remove from history

## Dependencies

- Run `npm audit` (or equivalent) before shipping new dependencies
- Prefer actively maintained packages with minimal transitive dependency trees
- Pin or lock versions (`package-lock.json` / `bun.lockb`) in production
- Review what a new package actually does before installing it

## HTTP Security Headers

Set these on every HTTP response:
- `Content-Security-Policy` — restrict script/style/image origins
- `X-Frame-Options: DENY` — prevent clickjacking
- `X-Content-Type-Options: nosniff`
- `Strict-Transport-Security` — HSTS for HTTPS endpoints
- `Referrer-Policy: strict-origin-when-cross-origin`

CORS:
- Never use wildcard `*` origins in production
- Explicitly allowlist trusted origins
- Restrict allowed methods and headers

## Rate Limiting & DoS

- Apply rate limiting on all auth endpoints and any expensive/side-effectful operations
- Validate file upload size (set a hard limit) and MIME type (check magic bytes, not just extension)
- Paginate all list endpoints — never return unbounded result sets

## Logging & Monitoring

- Log authentication attempts (success and failure) with timestamp and IP
- Do NOT log PII, passwords, tokens, or secrets
- Use structured logs (JSON) so they are machine-parseable
- Log at the appropriate level — don't silence errors in production

## Project-Specific Notes

Approved deviations (owner sign-off 2026-10-10, see `docs/PRD.md` section 13):

- Sessions are Better Auth database sessions in `httpOnly`, `Secure` cookies, not 15-minute JWTs. They are revocable server-side and never stored in browser storage.
- The Google OAuth callback uses a separate short-lived `SameSite=Lax` state cookie, because a `SameSite=Strict` cookie is not sent on the redirect back from Google. The session cookie itself is unaffected.

- The website read sends the address of a company's page to Jina Reader (`r.jina.ai`, no key) when that page arrives empty because a browser builds it from scripts (owner sign-off 2026-10-12). Only the address goes, after this app has fetched the page itself and checked the site's robots rules; what comes back is untrusted page text like any other. `WEBSITE_RENDERER=off` stops it.
- Pictures are decoded and re-encoded by `sharp` (native code) before they are stored. Only bytes that pass the magic-byte check for PNG, JPEG, GIF or WebP are handed to it, under a size cap, a 40-million-pixel limit and a five-second timeout. Pictures fetched from company websites, which are a stranger's bytes, are decoded only inside a background job. A picture the signed-in owner puts on a whiteboard is decoded inside the upload request, since the whiteboard needs the answer at once (owner sign-off with the plan, 2026-10-14); the limits are the same.
- "Find profile links" sends a person's full name and the name of their first company to Tavily (`api.tavily.com`) to look for their LinkedIn, X and GitHub profiles (owner sign-off 2026-10-12). It happens only when the owner presses the button, never by itself, and only when `TAVILY_API_KEY` is set; without the key the button is not shown. The key travels in a header that is never carried across a redirect. What comes back is untrusted: only addresses that are a profile on one of the three sites are kept, each title is shown as plain text, and nothing is saved on the person until the owner adds it. Searches are limited to 20 an hour, 900 in 30 days and one a minute for the same person.

- **Preview deployments (owner sign-off with the plan, 2026-10-26).** Each pull request is built by Vercel as a preview on one shared Neon branch, `preview`, copied from production on 2026-10-28, so a preview holds a copy of the owner's real data at a second address. Previews stay behind Vercel Authentication (Deployment Protection), so nobody signed out of the owner's Vercel account can open one. Preview's `DATABASE_URL` is a Vercel variable of its own pointing at that branch and is never production's, since every build runs the migrations (set on 2026-10-31 and tested: a preview build moved that branch and left production alone; until then previews used production's). Preview has its own `APP_ENCRYPTION_KEY` (since 2026-10-29), never production's, so the Google client and tokens copied with production's data cannot be opened there, and no `TAVILY_API_KEY`, so a preview sends nobody's name out; the schedulers call production only. **Not yet met as of 2026-10-31:** `AUTH_SECRET` and `CRON_SECRET` are still shared by Preview and Production and are to be separated by the owner in Vercel. `main` takes only a squash-merged pull request whose CI is green (a GitHub ruleset with no bypass), and secret scanning with push protection is on for the repository.

Project rules:

- Every table has `owner_id`; every server action and query calls `requireOwner()` and filters by it.
- User-supplied keys and OAuth tokens are stored encrypted with AES-256-GCM using `APP_ENCRYPTION_KEY`, decrypted only server-side at the moment of use, and never returned to the browser.
- `/api/jobs/tick` requires the `CRON_SECRET` bearer token, compared in constant time.
- Email bodies, attachments and fetched web pages are untrusted content. They are rendered as plain text only and can never authorize an action.
- AI tool permissions are enforced in server code, not in prompts. External actions always need explicit user confirmation.
- **Email text and free models (planned for Phase 6, owner's choice, 2026-10-31; a known conflict, not yet built).** Free models may keep or train on what they receive, and Google's user data policy limits passing Gmail data to third parties, with no exception for personal use. The owner chose to leave this to the person setting the app up over forcing a no-training model. Settings states what is known about the chosen model's data use; no email text reaches a model until that person ticks an acknowledgement that the provider may keep or train on it and that this may break Google's rules; the Privacy page says the same. Nothing technical enforces a no-training model.
- **The assistant's outside text (planned for Phase 6, 2026-10-31).** Calendar text counts as untrusted along with the content above, because anyone can send an invite. Once a conversation has read any, tasks, notes and memories need a tap for the rest of it; a Gmail draft keeps its undo card, because nothing leaves the account and the card shows recipient and subject. Replies are plain text with links built only by the server from tool results, and no outside images, so a hostile email can't leak data through a link or picture.
- Outbound fetches for enrichment must block private and loopback addresses.
- A link between a contact and a company is written only after both are checked against the owner. Saying a person a website names is an existing contact is accepted only for a pair the server itself offered for that company.
- A profile link found by name is added only if the stored search offered that address for that person.
- Archiving, restoring or deleting several records at once takes a list of ids from the browser: between 1 and 50, each a uuid, checked by zod in the action. Each id then goes through the same owner-filtered, audited service call as a single record, so an id that is not the owner's changes nothing.
- Which columns a list shows is kept in a cookie the browser writes (`columns-companies`, `columns-contacts`; not `httpOnly`, since it holds a preference and nothing private). The page takes from it only the names of that list's own columns and ignores the rest. Custom fields shown as columns (2026-10-26) are kept the same way in `columns-companies-custom` and `columns-contacts-custom`, which name the fields turned on by key; the page takes from them only keys of the owner's own fields of that kind (`customColumns`), and a value is drawn as plain text.
- A list sorted by a custom field (2026-10-26) names it in its address as `custom.<key>`, accepted only in that shape (`CUSTOM_SORT`: lowercase letters, digits and `_`, 1 to 60) and then only if it is one of the owner's fields of that kind (`customSortOf`); anything else sorts by name. The key reaches the query as a bound parameter (`customSortBy`), never written into the SQL, and the field's kind, not the address, decides how its values are compared.
- The page behind a whiteboard's drawing is kept in a cookie the browser writes (`board-paper`; not `httpOnly`, since it holds a preference and nothing private). The board's page takes from it only one of the four names in code (`paperOf` in `src/app/(board)/workflows/[id]/paper.ts`) and falls back to the dotted grid; the name becomes an attribute that a stylesheet rule matches, so nothing from the cookie is ever written into a style.
- A form opened in a panel says where it came from in two hidden fields, a record kind and a company id (`readOrigin` in `src/lib/form.ts`, strict: one of the known kinds, a uuid or nothing). The action never follows an address sent by the browser: it builds the way back itself from those and from the ids it has just saved, and the page it lands on checks the company and the person against the owner, and that the person is at that company, before showing either. An activity or task named in an address (`activity=`, `task=`) is shown only if it is the owner's; `send=` takes only `new`.
- A custom value is stored only for a field the owner defined for that kind of record, and only if it fits that field's kind and options; a form's other keys are never read. A suggested field is added by its key from the list in code, never from a label or options sent with the request. The full New forms of a company and a person (2026-10-26) read custom values exactly as the Edit forms do (`readCustomValues`), so the same holds when a record is created. A dropdown's option is removed (2026-10-26) by a server action that takes the field as a uuid and the option as a strict string of 1 to 60 characters (`removeFieldOptionAction`); inside one transaction the field is locked by owner and id, the option must be one it holds exactly and not its last, and only then is it taken off the list and cleared from the owner's records of that kind whose value is that option (compared as a bound parameter). It is audited as `field.option_remove` with the option and how many records were cleared. A custom value is set in place on Details (2026-10-26) by a server action (`setCustomValueAction`) that checks the owner and takes the kind of record from the fixed list, the record as a uuid, the field's key as a string of 1 to 60 characters and only the form's `value`; inside one transaction (`setCustomValue`) the field is found by owner, kind and key, the record is locked by owner and id, and the value is checked by the same `customValuesInput` the Edit forms use. Only that key is written, its name and value as bound parameters, so another field's value is never overwritten; an unchanged value writes nothing, and a change is audited as the record's `organization.update` or `contact.update` with that key's value before and after.
- A starter workflow is added by its key from the list in code (`src/modules/workflows/starters.ts`), never from a name or a drawing sent with the request. An owner has at most 50 workflows. Names and descriptions are drawn as plain text.
- **Approved deviation (owner sign-off 2026-10-13): a workflow's drawing is not checked field by field.** The rule above says to reject unknown fields. A drawing is a list of whiteboard elements (Excalidraw), each with dozens of fields that differ by kind and by version of the whiteboard, so a strict list of them would refuse every save after an update. Instead (`sceneSave` in `src/modules/workflows/schema.ts`): the envelope is strict (a version and a list of elements, nothing else), a drawing is at most 3 MB and 10,000 elements with at most 100 stages, and in each element everything the server reads or that could do harm is checked: the kind is one of nine (boxes, arrows, lines, free strokes, text, frames, pictures; never an embedded page or iframe), a picture's `fileId` is 1 to 64 letters, digits, `-` or `_` and a picture must have one (no other shape of id is stored, so none can be read back as a path), `customData` is nothing, or at most a stage's mark and a sticky note's mark: a stage's mark is one of the four statuses and, since 2026-10-13 (owner sign-off with the plan for sketches offered as stages), optionally a name of 1 to 200 characters for a stage made of handwriting, whose box holds no text; a sticky note's mark (since 2026-10-26, owner sign-off with the plan for whiteboard colours approved 2026-10-25) is `sticky: true` and nothing else; and `link` is kept only if it is an http or https address and dropped otherwise. The remaining fields (position, size, colours, stroke points) are stored as they came. They are never rendered as HTML by this app and never read by the server; they only go back to the whiteboard in the owner's own browser, which draws them on a canvas. A stage's name is the text in its box, cut to 200 characters, or else the name in its mark; either way it is drawn as plain text.
- The whiteboard saves through `PUT /api/workflows/<id>/scene`, one of the nine routes that change data with a session and are not server actions (a server action would flash the progress bar every two seconds; another is a brainstorm board's save, below; the other seven are the uploads below: a file and a picture on a whiteboard, a picture on a brainstorm board, a new material made with a file, a file added as a material's version, a file put in place of what a version held, and an invoice's file). It checks the owner, refuses any request whose `Origin` is not this app's own (`APP_URL`), which is what a server action does by itself, takes the id as a uuid, and updates only a workflow that is the owner's. A save names the version it was loaded at and is refused if the stored one has moved on. Saves are not written to the audit log, since one is made every few seconds while drawing; creating, renaming and deleting a workflow are. A GET of the same address gives the stored drawing to its owner only, with `Cache-Control: no-store`.
- The whiteboard is a third-party component (`@excalidraw/excalidraw`, MIT, pinned to 0.18.1) and runs only in the browser, on the workflow page. It is given no way to reach another site: its fonts are copied into this app at build time (`scripts/copy-board-fonts.mjs`) and the copies it lists on a CDN (esm.sh) are taken out of every font before it is made (`board-canvas.tsx`), its shared-library browser and its tool for embedding another site's page are turned off, and the CSP is unchanged (`font-src 'self'`, `connect-src 'self'`), so anything that slipped past would be blocked. The e2e suite fails if the workflow page asks another host for anything or logs an error. Four packages it depends on had open advisories at the versions it pins; `pnpm-workspace.yaml` overrides them to fixed releases (nanoid, lodash-es, katex, and since 2026-10-24 dompurify, through mermaid) and drops `sass`, a build tool it lists and never loads.
- A workflow is started on a company or a person only after the record is checked against the owner, and from a workflow only if that workflow is the owner's and a template (never another record's board). The browser names the record by kind and id (strict: exactly one of the two, a uuid) and the workflow by id; the drawing that is copied is the stored one. A record has at most 20 boards.
- A stage's status is never set outside the drawing (since 2026-10-17, when the record's chip on its own board replaced the Pipeline board and its `moveToStage` action). Moving the chip, choosing a place from its menu or "Move here" on a stage's card is a change to the drawing made in the browser (`statusesAfterMove` in `src/modules/workflows/stages.ts` works out the statuses from the drawing's own stages and arrows): it is saved through the scene route above like any other change, from the version the whiteboard loaded, and the server checks it as it checks every drawing (`sceneSave`). So it is not audited, as a status set on a box never was. The record's name and picture on the board come from the board as stored (`boardSubjectOf`, owner-filtered); the name is drawn as plain text and the picture is the owner's own logo or photo route.
- A workflow's icon (2026-10-14) is stored only as one of the keys listed in code (`WORKFLOW_ICONS` in `src/modules/workflows/icons.ts`), checked by zod in the action (`boardIcon`), with a check constraint on `workflow_boards.icon` that allows only a key's shape. It is drawn from a fixed map of icon components (`workflow-icon.tsx`); a stored key not in the map draws a placeholder, so nothing stored is ever rendered as markup or a class. Changing it is audited.
- A star on a record's board (2026-10-14) is set by a form that names a board as a uuid and a yes or no (`boardStar`, strict). The board must be the owner's and a record's own (a template has no star, also held by a check constraint); at most one board of a company or of a person is starred, held by two partial unique indexes, and the other star is cleared first in the same transaction. It is audited.
- The order of the workflows is taken as a list of 1 to 50 ids, each once, and kept only if it is exactly the owner's own templates; otherwise nothing is moved.
- A record's board leads back to its record by an address built on the server from the board as stored (after a delete, as it was stored), never from one the browser sent.
- **File uploads (the app's first; owner sign-off with the plan, 2026-10-14).** A file goes on a box of a whiteboard through `POST /api/workflows/<id>/attachments`, a route because a server action takes a megabyte at most. It has the scene route's guards (the owner's session, an `Origin` that is this app's own, the id as a uuid) and takes a form with exactly a file and an element id. A request is turned away by its stated size before any of it is read (`Content-Length` is required), then by its real size: 4 MB a file. The kind is read from the bytes alone (`fileType` in `src/modules/files/sniff.ts`); the name and the type the browser sends are never believed. Kept: PDF, PNG, JPEG, GIF, WebP, and Word, Excel and PowerPoint files, told apart by the names in the zip's own list, which is walked with every offset checked and at most 5,000 entries, and never unpacked. Refused: everything else, which includes whatever can carry script (SVG, HTML), old binary Office files, plain text and plain archives. The server does nothing else with the bytes: it does not parse, convert or preview them. Limits: 200 MB of stored files an owner (the same bytes stored once), 50 links and files a board, 30 uploads a minute. A file goes only on a box (a rectangle, diamond or ellipse) of the owner's own drawing as stored. Adding and removing are audited with the title, kind and size, never the bytes.
- A stored file is served by `GET /api/workflows/<id>/attachments/<attachmentId>` to its owner only, found by board and attachment together so an id from another board gives nothing. It is sent with the kind read when it was stored, `nosniff` (every response has it), `Cache-Control: private, no-store` and the policy every `/api` answer carries (`default-src 'none'`), under which a browser shows a PDF or a picture and can run nothing. A PDF or a picture is sent to be shown in the tab; an office file is sent as a download. The name it is saved under is the attachment's title, percent-encoded. A title is the uploaded name without control characters and slashes, cut to 200 characters, and is drawn as plain text.
- **Pictures on a whiteboard (owner sign-off with the plan, 2026-10-14).** A picture goes up through `POST /api/workflows/<id>/pictures`, with the guards of the file upload, which every upload route shares in one place (`upload` in `src/lib/upload.ts`): the owner's session, an `Origin` that is this app's own, the id as a uuid, a required `Content-Length` checked before the body is read, and a form of exactly a file and the whiteboard's id for the picture (1 to 64 letters, digits, `-` or `_`). The bytes are never stored as they came: they are read as a picture and written out again as WebP, no larger than 1440 px on the longer side and without the file's metadata (see the note on `sharp` above). What cannot be read that way is refused, which includes SVG, the one kind of picture the whiteboard accepts that can carry script; the whiteboard then takes it off the drawing and says why. Limits: 4 MB a picture as sent, 100 pictures a board, 60 a minute, and the 200 MB an owner's files may take. The board must be the owner's. Adding is audited with the kind and size, never the bytes.
- A stored picture is served by `GET /api/workflows/<id>/pictures/<key>` to its owner only, found by board and id together, so a picture id written into a drawing is only ever looked up among that board's own pictures of that owner and naming another board's gives nothing. It is sent with the stored kind (`image/webp`), `nosniff`, the policy every `/api` answer carries and `Cache-Control: private, max-age=31536000, immutable`: a board's picture under one id is written once and never changed, and `private` keeps it out of any shared cache. The page turns it into a `data:` address for the whiteboard, which the page's policy already allows for pictures (`img-src 'self' blob: data:`).
- A picture that nothing in the stored drawing shows is removed when the whiteboard is next opened, by a server action and not by a GET, and audited as the system's. One stored in the last ten minutes is left: the drawing that shows it may still be on its way from a page that was just closed.
- A link on a box is stored only as an http or https address (`httpUrl`); an address typed without its start has `https://` put before it, which no other kind of link survives. It opens in a new tab with `rel="noopener noreferrer"`.
- What a box no longer in the stored drawing carried is removed when the whiteboard is next opened, by a server action and not by a GET, and that removal is audited as the system's.
- A note on a box (`workflow_notes`, 2026-10-14) is added by a server action that names a board as a uuid, an element and the note, checked by zod (`noteBody` in `src/modules/workflows/schema.ts`: trimmed, 1 to 2,000 characters). It goes only on a box (a rectangle, diamond or ellipse) of the owner's own drawing as stored, found the way a link or a file is (`boxRefusal` in `src/modules/workflows/attachments.ts`), and a board carries at most 200. A note is removed by a board and a note id together, so an id from another board gives nothing. It is drawn as plain text only (line breaks kept by CSS, never turned into markup), adding and removing are audited with the note's text, and the notes of a box no longer in the stored drawing go when the whiteboard is next opened, as above.
- **Materials (2026-10-16).** A material's name, type and description are checked by zod in the action (`materialInput`, strict): the type is one of the ten in code, also held by a check constraint on `materials.type`; the name is unique per owner without regard to case (citext and a unique index, checked first under a lock per owner). Every change finds the material by owner and id inside its transaction and is audited; an owner has at most 500 materials and a material at most 50 versions. Names, descriptions and labels are drawn as plain text.
- A material's version is a link or a file. A link is stored only as an http or https address (`httpUrl`; one typed without its start has `https://` put before it) and opens in a new tab with `rel="noopener noreferrer"`. A file goes up through `POST /api/materials/<id>/versions` with the guards every upload shares (`upload` in `src/lib/upload.ts`: the owner's session, an `Origin` that is this app's own, a required `Content-Length` checked before the body is read) and a form of exactly a file and a label of 1 to 100 characters; the id is taken as a uuid. The kind is read from the bytes alone (`fileType`), the same kinds as a file on a box are kept, at 4 MB a file, 30 uploads a minute and the 200 MB an owner's files may take, the same bytes stored once. The material must be the owner's. Adding and removing are audited with the label, title, kind and size, never the bytes.
- A material can be made with a file as its first version (2026-10-22) through `POST /api/materials`, with the guards every upload shares and a form of exactly a file, a name, a type, a description and a label, checked by the same strict `newMaterialInput` as the New material form (with no link). The file is checked as above before anything is written, and the material and its version are written in one transaction, so a refused file leaves no material.
- A version is edited in place (2026-10-22). Its label can always change, by a server action checked by zod (`versionEdit`, strict: a label and an optional link, read as `httpUrl`). What it holds changes only while it has never been sent: a link in place of a file (the file is then freed if nothing else points at it), or a file in place of a link or another file through `PUT /api/materials/<id>/versions/<versionId>`, with the upload guards, both ids as uuids, a form of exactly a file and a label, and the checks and limits of a new version's file. Whether the version was sent is checked under the material's lock; a sent version's link or file is refused (`sent`), so a send always says what went out. Every edit finds the version by owner, material and version together and is audited with what it held before and after, never the bytes. The 30 uploads a minute are counted from the audit log, where every stored file is recorded with its kind, so a file put in place of another counts as one added.
- A version's file is served by `GET /api/materials/<id>/versions/<versionId>` to its owner only, found by owner, material and version together, so an id from another material gives nothing. It is sent as a file on a box is: the kind read when it was stored, `nosniff`, `Cache-Control: private, no-store` and the policy every `/api` answer carries; a PDF or a picture is shown in the tab, an office file is downloaded under its uploaded name, percent-encoded. A stored file is deleted only when no box, picture (on a workflow or a brainstorm board) or material version points at it (`dropUnusedFiles`).
- **Material sends (2026-10-18).** A send is logged by a server action checked by zod (`sendInput`, strict): a version as a uuid, a time typed to the minute and read in the owner's time zone, a channel that is one of the five in code, 1 to 20 people as uuids (each once), an optional company as a uuid and a note of at most 2,000 characters; a status cannot be sent with it. Inside one transaction the version must be the owner's, its material is locked, and every person and the company must be the owner's, or nothing is written. The channel and the status are also held by check constraints on `material_sends`. A status is changed by a server action that takes the send as a uuid and one of the five statuses, and only on the owner's send. Logging, a status change and a removal are audited (with the people, company, note and which older sends were marked superseded). At most 30 sends are logged a minute. A version that has been sent cannot be removed and keeps what it holds (checked under the material's lock); deleting the material takes its sends with it, and the dialog says so. Since 2026-10-22 sends are logged and shown only on a company's and a person's Activity tab: a send is drawn on a timeline from the `timeline` view, which takes its title from the material's name and the version's label, all as plain text; it links only to its material's page, built from the stored id, and its remove button sends only the send's id, removed only if it is the owner's.
- **Search in the command palette (2026-10-18).** A server action (`searchEverythingAction`) checks the owner and takes the typed text as a string of at most 100 characters, checked by zod. For the full-text match the text becomes tsquery tokens of letters and digits only (`prefixTsQuery`), so nothing typed is read as tsquery syntax; LIKE patterns are escaped (`likePrefix`, and the same escape for a match anywhere in a name); the text reaches `word_similarity` and every other comparison as a bound parameter. Every query filters on `owner_id`, and returns at most 5 rows of each kind; text under 2 characters or with no letter or digit searches nothing. Labels and hints are drawn as plain text, and each result's address is built on the server from the stored id with one of seven fixed patterns (brainstorm boards since 2026-10-24); the browser sends only the text.
- **Brainstorm boards (2026-10-24).** A brainstorm board is a whiteboard of the owner's own (`brainstorm_boards`), on no company and no person. Its name is checked by zod in the action (`brainstormName`, strict: 1 to 100 characters), unique per owner without regard to case (citext and a unique index, checked first under a lock per owner), and drawn as plain text; an owner has at most 200 boards; its icon is a key from `WORKFLOW_ICONS`, checked by zod (`brainstormIcon`) and by a check constraint on its shape, as a workflow's is. Creating, renaming, the icon and deleting find the board by owner and id and are audited. Where each field's value came from (`field_provenance`, typed or read) goes with the value picked, the logo with its pick, and the website reads (and the people they found) with the website kept. Every row that pointed at the other company is moved to the kept one or, for a person at both, dropped in favour of the kept place; the company keeps one primary contact and one starred workflow. The other company is then deleted, and one `organization.merge` audit row holds both as they were and the kept one after. The page it lands on is built on the server from the kept id. The merge view shows names, values and counts as plain text, and the address that opens it (`company=…&merge=`) shows nothing unless both companies are the owner's.
